# 持仓催化剂日历追踪

> 这份文档有两部分。**第一部分是写给你（个人投资者）看的**，用大白话讲清楚这个技能帮你干什么、有什么用——读完这部分就够了。
> **第二部分是写给 AI Agent 的执行规范**（术语密集、纪律条款多），普通用户不必读。

---

# 第一部分 · 给你看（人话版）

## 一、它帮你解决什么麻烦

你手里拿着几只股票，接下来几个月有几件**板上钉钉会发生的事**：公司要发财报、限售股要解禁、要开股东大会、回购方案要到期……

这些事公司早就公告过，日期是确定的。真正的麻烦是：公告散落在各家公司的公告流里，没人帮你汇总。等你刷到消息，往往已经过了。

这个技能只做一件事：**把你持仓未来几个月「确定会发生」的日子排成一张表，按日期先后排好。**

## 二、你能拿到什么

- **一张按日期排好的表**：哪天、哪家公司、什么事，一目了然；
- **每个日期后面挂着一个出处**——公告编号、监管函件号或具体法条，你可以自己点回去核对，**不是 AI 凭印象编的**；
- **一份「未来 30 天要盯什么」摘要**，方便你提前安排；
- **（可选）到日子自动提醒你**，还能顺带跑一份该事件的深度研究报告（这个要花积分，见第五节）。

## 三、怎么用

一句话就行：

> 「我持有沪电股份、恺英网络、领益智造，帮我看看未来三个月有什么日子要盯」

你也可以指定时间窗（不给的话默认未来 90 天），或者只关心某一类事件（比如「只看财报和解禁」）。

## 四、三条硬保证

1. **表里的每个日期都查得着出处。** 公司公告里没明写的日期，一个都不会出现在表上。哪怕是「公告日 + 360 天」这种看起来很合理的推算，也一律不算数——推算出来的日期不可核，就不进表。
2. **只报日子，不评好坏。** 它不会告诉你这件事是利好还是利空，也不会说该买还是该卖。判断留给你。
3. **鸡毛蒜皮的事不占版面。** 像「补选独立董事」「续聘会计师事务所」「修订公司章程」这种走流程的议案，就算日期是真的也不进表——免得你被一堆没信息量的提醒淹没。真正有内容的（分红、重组、大额担保授信、股权激励等）才会入表，而且会写清楚是哪个议案让它值得盯。

## 五、要花多少钱

| 项目             | 费用                     |
| -------------- | ---------------------- |
| **排日历本身**      | 不消耗 Cue 积分（走公开披露数据）    |
| **深度研究报告**（可选） | **消耗积分**，单次耗时约 3–15 分钟 |
| **自动提醒**       | 免费                     |

凡是花钱的动作，**动手前一定会先告诉你耗时和消耗，你点头才跑**。不会在你不知情的情况下偷偷扣费。

积分用完了怎么办（按成本从低到高）：**等次日免费额度**（每天送 10 分）→ **邀请好友得积分**（打开 [cuecue.cn](https://cuecue.cn/) 首页，点左下角「获取专属邀请链接」分享给好友）→ **直接充值**（[cuecue.cn/pay](https://cuecue.cn/pay)）。

## 六、它不做什么

- 不推荐股票，不给买卖点，不做择时；
- 不判断某个事件是利好还是利空；
- 不把小道消息、传闻、"据说要……"当成事件写进表；
- 不会替你下单，也不做自动交易。

一句话：**它是个日程表，不是分析师。给你日子和出处，判断留给你。**

## 七、常见问题

**Q：为什么我的持仓有些事查不到（显示「未检索到」）？**
A：大概率不是漏了，而是**没有符合标准的日期**。以解禁为例：公开渠道上的解禁日大多是按限售安排推算出来的「预计」日期，不是公司明写的完整日期——按本技能的规矩，推算的日期一律不进表。宁可空着，也不给你一个对不上的日期。

**Q：能不能顺带告诉我这次财报好不好、该不该卖？**
A：不能，这是它的设计边界。它只负责告诉你「10 月 28 日发财报」这件事本身。要看业绩兑现度的分析，得用另一个专门的技能。

**Q：表上的日期会变吗？**
A：会。预约披露日可能被公司改期。所以提醒触发时会再核对一次当日是否已实际披露，并明确标注「以当日实际披露为准」。

**Q：我是第一次用 Cue，需要准备什么？**
A：如果只是排日历，什么都不用准备。如果想跑深度研究报告，需要先注册 Cue 拿一个 API Key（[cuecue.cn/api-key](https://cuecue.cn/api-key?src=github-catalyst-calendar)）并装好运行环境——AI 会一步步引导你，并在开跑前先检查环境是否就绪。

# 第二部分 · 给 Agent 看（执行规范）

> 以下为执行契约，术语与纪律密集。交付的是**带披露锚的日程表**，不是交易信号。日历上每一个日期都必须能回指一条在场公告或一条法条。
> 铁律与通道契约语法继承姊妹件 `cn-earnings-note`；本件最大风险=**日期幻觉**，全部设计围绕它。

## 0. 什么时候用 / 不用

| 你要                      | 用什么                           |
| ----------------------- | ----------------------------- |
| 「未来三个月这些持仓各有什么确定的日子」的日历 | **本 skill**                   |
| 日历排完后，到了日子要被提醒、并顺带跑深度研究 | **本 skill §7 `+alert`**       |
| 某只票的深度点评/兑现度对账          | `cn-earnings-note`（覆盖账本在其契约内） |
| 选股、择时、利好利空判断            | 不做——褒贬类表述全禁（铁律 3）             |
| 传闻/预期类「事件」              | 不做——未披露不入表（铁律 2）              |

## 1. 铁律

1. **输出是 AI 初稿**：标题后前 5 行内含**两项**（机检①）——「AI 初稿」字样，以及「不构成…投资建议」这句声明短语（此前本文只写了前一项，实际缺后者同样 FAIL）。**评级概念零容忍是机检事实**：评级词面=`RATING_RE` 现值（常见例：买入、增持、目标价——**例不穷尽**，全量一条命令自查见 §3 `+check`）。豁免只有两条口径，都写在码里：①**类型列整列不扫**（封闭枚举内的中性披露词组，如「减持计划预披露」）；②**按词形豁免**=`OFFICIAL_USAGE_RE` 现值（官方披露词组形，光杆「增持/减持」不豁免）加三个分类学词组（解禁减持一类）。扫描面=表格的事件/状态/窗外余档/来源锚四列 + 非表格正文 + sources 的 claim；日期列不在这一道（它由机检④管格式）。本件比姊妹件更严：没有「[待人工] 留白位」这回事，评级在这里根本不适用。
2. **入类第一闸（二选一，否则根本不入日历）**：①已有披露在场**且含明确 `YYYY-MM-DD`**；或 ②`statute` 规则推导**且适用条件在锚内可判**（条件不满足即拒推，快报类无条件者不推）。**未披露的推测事件、任何日期算术**（如「公告日+360 天」推算截止日——这类推算全线不产行，仅公告原文明写完整日期才可入，锚=该公告）一律不是条目。**过第一闸后还有第二闸（信息量闸，判据见 `references/event-taxonomy.md` §1.5）**：日期真实但议案零信息量者同样不入表——仅含「因个人/工作原因辞职后的独董、董事、监事补选」「续聘原审计机构」「章程/内控制度修订」「变更全称、简称、注册地址」等例行议案的股东会免入；命中实质议案（重组、分红、担保额度、大额授信、激励草案等）者入行，且**事件列必须点名那个让它入表的议案**，只写「第 N 次临时股东会」=读者看不出为何要盯，按不合格回改。免入须在 `progress.md` 记弃条并写明命中哪一项，**不得写成「未检索到」**——前者是主动过滤，后者是取数空档，混写等于把过滤伪装成空档。
3. **只陈述，不判断**：禁预判涨跌与一切褒贬；禁词面=本包 `BANNED_RE` ∪ `RATING_RE` **两条现值**（常见例：利好、利空、抄底、必涨——**例不穷尽**）。本文不再说它是「姊妹件全集+本件六词」——两包各存一份拷贝、互不继承，一边改词另一边不会跟着变，所以全量只能查本包脚本（`+check` 那条命令）。另有一道本文此前完全没提：**自白词道**——事件列与状态列含 `HALLUCINATION_RE` 现值里的措辞（常见例：预计、有望、通常、大概率）即报，理由是「锚证事件在场、不证日期」；这类内容改道「已发生动态」或不产。事件的中性陈述例：「回购方案期限截止日（公告明写）」「问询回复截止日」。
4. **无锚即删条**：数字与日期回指不了 `sources` 的条目，直接从日历删除并在台账记弃条原因；**日期一律 `YYYY-MM-DD` 全格式**（机检④），窗口外但确有必要的条目填**独立第 5 列「窗外余档」**（值=空 或 `窗口外余档(YYYY-MM-DD，早于/晚于窗口端)`；余档列空置即 FAIL——窗外是日期幻觉高发口，锚列永远纯锚不承载余档注）。
5. **花之前必问**：cue-research ≤1 次（解禁/减持原表）与一切计费动作同姊妹件纪律——发起前报告耗时与消耗，只转述服务端计费事实。**本条同样管 §7 的深度研究**：那类动作由无人值守的提醒触发、届时无法中途征询，故授权必须在**设置提醒的阶段**一次性拿齐（§7.2）。积分不足（`INSUFFICIENT_CREDITS`）时的处理见 §7.7——**只丢一个错误码不算交付**。

## 2. 输入契约（≤4 问，逐条带默认值）

- **主体集**：官方中文全称或代码，≤10 个（逐个过消歧：以本次 `disclosure_cn` 返回的官方全称/代码核对主体唯一性，一名多主体时列候选让用户点、不代选）
- **窗口**：`YYYY-MM-DD~YYYY-MM-DD`，缺省=今起 90 天（缺省只作用于输入对齐；`+check` 一律传定稿后的字面窗口，禁读墙钟，见 §3）
- **关注类**（可选）：如「只看回购与分红」——缩窄 §3 取数面，不扩
- **输出目录**：默认 `./calendar-<日期>-<n>主体/`

## 3. 管线（五段+门禁，可续跑；开工建 `progress.md` 台账）

- `+scope`：主体集消歧+窗口落表；逐主体 `disclosure_cn` 拉窗口内公告清单存锚。
- `+events`：按 `references/event-taxonomy.md` 逐类取数——入类先过第一闸（该文件 §1），再归类型封闭枚举：判定=`check_calendar.py` 里 `EVENT_TYPES` 现值，该文件 §2 表是给人读的镜像，两者不一致时以现值为准（一条命令自查见 `+check` 行）；`buyback`/`esop`/`disclosure_cn`/`regulatory_cn` 域直查（工具与入参 schema 一律当场发现，域清单与工具面以 catalog 现值为准，本文不抄）；解禁/减持原表按缺口决定是否发起 research ≤1（L3 标注+L1 前置见分类学 §4.3）；**满窗稀疏时的显式升级路径**：原表域内直查零命中→不静默留空，向用户报「升 research 一次的预计耗时与消耗」并默认征询，同意才升、拒绝则该维持「未检索到」——空日历合法，但「可升级」的路要摆到用户面前。股东大会（含临时；须再过分类学 §1.5 第二闸——仅含补选独董、续聘原审计机构等例行议案者免入，命中实质议案者入行且事件列点名该议案）/业绩与投资者说明会/风险警示（ST/*ST）实施与撤销生效日/停复牌生效日四类为后收项，镜像表内同列。无事前日期的进度类披露（回购 1%/2% 节点等）入「已发生动态」附注区，不占日历行。omni 仅在公告原文必须解析时调用（域面 section 全文优先，三级路径同姊妹件）。**`margin` 域不入列**——能力面=两融折算率，与事件日历无关（Q1 对账定案）。
- `+derive`：法定期限类仅对**适用条件在法条锚内可判**者推导（如定期报告披露期限条款含报告期类型与主体类别），**每条挂 `statute` 当场取回的法条原文锚，锚值规格=`statute:<法名>第N条(<要点短引>)`**——名称+条号+短引三件齐，禁裸串；sources 对应行 `kind=statute` 且 ref 可复核（反编造法定锚）；规则文本不写死在日历里，条件不可判的期限（如未分主体的快报类）拒推不落行。
- `+build`：按主体节组装 `calendar.md`——**形制契约**：表格六列顺序钉死 `日期|事件|类型|状态|窗外余档|来源锚`（锚列永远末列纯锚）；**节名规则**：主体节=一级 `##` 且标题**不属于保留词封闭集 `{未来30天要盯 | 已发生动态 | 附录}`**，摘要/附注区的识别只按保留词、禁拿字面「主体」当节前缀；「未来30天要盯」段只列不评；「已发生动态」区收无事前日期的进度类披露（带锚不占日历行）；附录=与 `sources.jsonl` 一一对应的来源索引。
- `+check`（不过不交付）：
  ```bash
  python3 scripts/check_calendar.py <calendar.md> --sources <sources.jsonl> --window <YYYY-MM-DD~YYYY-MM-DD> --evidence <evidence目录>
  ```
  **`--window`/`--sources` 必传、`--evidence` 正式管线必传全量**（checker 侧 --evidence 为选传以容旧产物，但**文档不写它就等于这道闸形同虚设**，故正式调用式一律把它摆上；window 字面值=输入契约定稿值；checker 禁读墙钟——「今起 90 天」只是输入缺省，进入机检前必须落为显式窗口，否则历史产物隔天重跑结论漂移）。机检要点：①声明行 ②**六列**表头状态机+数据行逐行锚校验（锚型形状=`AN_RE`/`SIX_RE`/`URL_RE`/`LETTER_SEG_RE`/`CONV_RE`/`STATUTE_SPEC_RE` 现值，按类型×锚型映射 `TYPE_ANCHORS` 判定，无 fallback 放行；**六位以上纯数字是合法锚形之一，所以"页上有数字"不等于"这行有锚"**，读者要核的是那一列指不指得回披露）③禁词+**评级词零容忍（豁免口径两条见铁律 1：类型列不扫 + 官方词组按词形）** ④日期全格式、按主体节非降序、窗外条目余档列空置 FAIL ⑤正文锚↔sources 双向可解析（「被引用」只认来源锚列解析键，附录文本出现不算）+类型×锚型映射（监管类必函件号，法定类必 statute）⑥主体数 ≤10（判定=码内上限） ⑦**锚∈evidence**：每条锚（公告索引号/函件号/法名条号三式）须在 `evidence/` 某快照内原文匹配到，statute 适用条文文本亦须在档——断链=FAIL；交付物复核面固定挂「evidence 抽 3 对原文」人审行（语义真值止于证据层，快照造假归人）。FAIL 回改复跑。词面域一条命令自查，任意目录整行粘贴即跑、命令自带安装后路径；装在别处把 `~/.workbuddy/skills/` 换成你的技能安装目录，Windows 路径形如 `C:\Users\<用户名>\.workbuddy\skills\catalyst-calendar\scripts\check_calendar.py`，两条命令都走 POSIX 工具，Windows 请在 Git Bash/WSL 内跑）：`grep -n -A3 "BANNED_RE = \|RATING_RE = \|HALLUCINATION_RE = \|OFFICIAL_USAGE_RE = \|EVENT_TYPES = \|TYPE_ANCHORS = \|SIX_RE = " ~/.workbuddy/skills/catalyst-calendar/scripts/check_calendar.py`；守护样清单同形现跑：`bash ~/.workbuddy/skills/catalyst-calendar/scripts/fixtures/run_fixtures.sh`——本文不抄域清单、不抄类型条数、也不抄守护样条数，跑什么是什么。**绿灯不证防线**：机检全过只证形状合规，不证语义为真。
- `+alert`（机检 PASS 后**必做**、不待用户问，细则见 §7）：主动提出按日历设当日提醒——**按日聚合**、默认盘后核查档、执行内容自包含；深度研究属计费动作，**须先报告耗时与消耗并征询**，同意才写进提醒；已建提醒（含任务 id 与授权来源）记入 `progress.md`。

## 4. 输出契约

**开口请带上时点，输出标数据日期**：请求里给出报告期／基准日或回看窗口；成品首行标注**数据日期**，当它与用户所指日期不一致时，正文禁用「今日」「最新」，一律改写为「截至 <日期>」。

**未见于本次返回的一律写「未检索到」**：参数名、字段名、枚举值没有出现在本次工具返回里的，不得凭印象填写；写「未检索到」并记入待核清单或覆盖率账，不得留空顶替。

```
calendar-<日期>-<n>主体/
├── calendar.md      交付物：声明行+主体节（六列正排表）+30 天要盯段+已发生动态附注区+附录来源
│                    （节名规则与保留词封闭集见 §3 +build 形制契约）
├── sources.jsonl    行式同姊妹件契约（id/kind/ref/claim/confidence/asof；法定行 kind=statute、
│                    ref=法名+条号；research 件带 conv_id+路径）
├── evidence/        域直查原始快照（一笔查询一个文件 `evidence/<kind>-<query摘要≤40字>-<YYYYMMDDTHHMMSS>.json`，原样落盘禁转写摘要冒充，append-only 不覆盖；机检第⑦道按档内原文匹配）
└── progress.md      台账：各段进度+弃条记录+research 实况
```

## 5. 通道依赖与降级

首次开通 Cue 三步同姊妹件（注册→api-key→装 skill；不装不报错）——**取数通道不装不报错，但深研通道不装会真的跑不起来，开通与预检见 §7.6**。降级路径：data-mcp 不可得→用户贴公告清单（标 L2 直供）；降级取数（用户直供清单等）同样落 `evidence/` 并标来源级别，不留无痕通道。research 不发起→解禁/减持类整类标「未检索到」，**不以常识补日**。全降级仍可用，代价是日历覆盖度。

## 6. 边界与拒答

- 「帮我挑什么时候卖」→ 拒绝：日历陈述日子，不产出择时判断。
- 「把传闻/预期的事件加进表」→ 拒绝并引铁律 2。
- 主体集 >10 个 → 提示拆分（保取数质量与每主体锚完整）。
- 「设个自动盯盘、到点自动买卖」→ 拒绝：提醒只报日子与事件，不产出交易动作（同铁律 3）。

## 7. 交付后动作 `+alert`（机检 PASS 后必做，不待用户问）

日历交付不是终点——排完没人盯等于没排。机检 PASS 后**必须**主动向用户提出按日历设提醒，把建议表摆出来，**不静默收尾**。

### 7.1 建议表与聚合口径

- **按日聚合**：同一日的多个主体事件合并为一条提醒（当天要做的事相同），不按行拆、不一日多条。
- 建议表形制：`事件日 | 主体（代码） | 事件 | 建议时点 | 是否附带深研`——逐行列出让用户勾，不代用户全选。
- **日期一律取日历行的字面日期**，禁推算、禁「提前一天」这类算术（同铁律 2）。
- 两档时点（默认给盘后档，可由用户改）：
  - **盘后核查档** `<事件日>T19:30`：事件已发生 → 提醒＋核对实际披露＋（已授权）深研；
  - **盘前预瞻档** `<事件日>T08:30`：只提醒不深研——事件尚未发生，此时研究无的放矢。

### 7.2 计费授权（硬闸，先问后设）

深度研究属计费动作（cue-research：单次耗时约 3–15 分钟、消耗积分，**以服务端返回为准**，本文不报死数）：按铁律 5，**创建提醒前须先向用户报告耗时与消耗并征询**。

- 同意 → 把研究动作写进提醒的执行内容；
- 未同意 → 提醒只做陈述，末尾固定附一句「如需就该事件跑深度研究请回复确认（将消耗积分、耗时约 3–15 分钟）」；
- **禁止**在提醒里静默发起计费动作：无人值守运行时无法中途征询，授权必须在设置阶段一次性拿齐。积分耗尽后的处理见 §7.7（含无人值守分支）。

### 7.3 提醒的设定形态（执行内容必须自包含）

- 用所在客户端的定时/自动化能力建**一次性**任务（一次性＝`scheduleType=once` + `scheduledAt=<事件日>T<时点>`），`status=ACTIVE`，工作目录指向日历所在目录。
- 命名：`催化剂日历提醒 · <YYYY-MM-DD> · <主体简称…>`。
- **执行内容必须自包含**（未来那次运行看不到本次对话）：写明主体官方全称+代码、事件名、日历文件绝对路径、证据目录、是否跑研究、研究命令与报告落盘路径。缺任一项＝未来那次运行必然跑偏。
- **写入研究命令前必须先过 §7.6 通道预检**：runner / Key / 服务任一不就绪，禁止把裸研究命令写进提醒——无人值守触发时失败无人补救，只能按 §7.6 的兜底形态写。
- 研究命令形（参数以 `cue-deep-research` 现值为准，不抄死）：
  ```bash
  python3 ~/.cue/cue-skills/cue-research/scripts/research_run.py \
    --query "<主体全称（代码）> 于 <事件日> 的<事件>：已披露的事实要点、与公开预期的差异" \
    --output ~/cue-reports/$(date +%Y-%m-%d-%H%M)-<主体>-<事件摘要>.md
  ```
- **防关机漏跑（设定时必说，不待用户问）**：定时/自动化任务依赖**设备开机且客户端在运行**——关机、休眠或客户端没启动就**不会触发**，且多数实现不做补跑，**错过即永久错过**。故设提醒时须主动提示用户三件事：
  - ① 时点尽量落在**上班期间**（如 `T09:30–T18:00`），此时设备通常在线；
  - ② 若常不在电脑前，改用**手机端小程序**保持在线接收消息（在线面比电脑宽、关机风险低）；
  - ③ 只能设在下班后/深夜等易关机时段时，**必须明确告知**「届时保持设备开机且客户端运行，否则这条提醒等于没设」——**不告知＝把漏跑风险闷在用户身上**。
- **无定时能力时降级**：在交付时给出提醒日期清单让用户自行设闹钟，不谎称已设。


### 7.4 提醒内容纪律

- 仍守铁律 3：只陈述日期与事件，**不预判涨跌、不给买卖建议**。
- **研究报告不回填 `calendar.md`**——两者分开交付，回填会撞形状闸与禁词闸。
- 当日事件若实际未发生（预约披露改期、会议延期）：提醒里写明「以当日实际披露为准」并回指日历锚；**不替用户改日历行**——改期须新公告到场才建行（同铁律 2）。

### 7.5 台账

已建提醒记入 `progress.md`：事件日、时点、名称、任务 id、是否含研究、授权来源（哪一轮对话同意）。后续 update/delete 一律按 id，不按名称模糊匹配。

### 7.6 Cue 深研通道预检（新用户开通道，设提醒前必做）

§7.3 的研究命令**假设 runner 已在位、Key 已配、服务健康**。这三项对老用户常成立、对新用户默认全不成立——而提醒是**无人值守**触发的，届时失败没有任何补救窗口。故本节是硬前置，不是可选项。

本节三步：**① 预检 → ② 开通道（不就绪时）→ ③ 兜底写法**。设提醒前全部走完，缺一步不许把裸研究命令写进提醒。

**第 1 步 · 预检 —— 一条命令查三件事**（读 `~/.cue/config.json` 或 `CUE_API_KEY` 环境变量，**不打印 Key 值**）：

```bash
CUE_KEY=$(python3 -c "import json;print(json.load(open('$HOME/.cue/config.json'))['api_key'])" 2>/dev/null || echo "$CUE_API_KEY")
echo "=== 检查1 runner ===" && [ -f "$HOME/.cue/cue-skills/cue-research/scripts/research_run.py" ] && echo "已安装" || echo "未安装！"
echo "=== 检查2 API Key ===" && [ -n "$CUE_KEY" ] && echo "已配置" || echo "未配置！"
echo "=== 检查3 Cue 服务 ===" && curl -sS --max-time 10 "https://cuecue.cn/api/health" -H "Authorization: Bearer $CUE_KEY"
```

| 检查项 | 就绪判据 | 不就绪时的处理 |
|---|---|---|
| runner | 打印 `已安装` | 走第 2 步 ② 装 runner |
| API Key | 打印 `已配置` | 走第 2 步 ① 取 Key |
| 服务 | 返回 `{"status":"healthy"}` | 等 5 分钟重试；仍不可用则本轮**不设带研究的提醒** |

**第 2 步 · 新用户开通道 —— 三步**（口径以 `cue-deep-research` 现值为准，不抄死）：

- ① **注册后免费创建 Key** —— [cuecue.cn/api-key](https://cuecue.cn/api-key?src=github-catalyst-calendar) 免费注册账号后点击「创建 API Key」，生成 API Key 后一定要点击「复制」并粘贴发送给您正在使用的智能体。计费事实只转述服务端口径：新账号送免费积分、每天再免费送 10 分，**实际扣数以服务端返回为准**（同铁律 5，本文不报死数）。
> **API Key 只能由用户本人创建**：Agent 既不能代生成、也无权查看用户的 Key。检测到未配置或失效时，按以下话术告知用户：**「点击『创建 API Key』，生成 API Key 后一定要点击『复制』并粘贴发送给我。」** 然后等待用户提供，**禁止声称"我去生成/查看"**。
- ② **装 runner** —— 跑 `cue-deep-research` 自带的一键安装脚本 `bash setup.sh`（检查依赖 → 克隆 runner → 验证 Key → 测试连通性；内置 GitHub / Gitee 双源自动切换）。依赖仅 `git` + `python3` + `curl`，Python 只用标准库。装完 runner 落在 `~/.cue/cue-skills/cue-research/scripts/research_run.py`。
- ③ **验证** —— 重跑第 1 步预检，三项全绿才算开通道完成。

**第 3 步 · 兜底形态 —— 通道未就绪时不许写裸研究命令**：

- 通道三项未全绿 → 提醒**降级为纯陈述**（同 §7.2「未同意」分支），末尾固定附一句「如需就该事件跑深度研究请回复确认（将消耗积分、耗时约 3–15 分钟）」，并**同时**告知用户先按第 2 步开通道；
- 已确认通道就绪、但届时可能波动 → 研究命令写成**带预检分支**的形态：先判 runner 与 Key，缺失即跳过研究、只做陈述并回报「Cue 通道未就绪，本次未跑研究」，**不静默失败、不假装跑过**；
- **禁止**用常识或通用检索冒充 Cue 研究报告交付——报告须带 Cue 的溯源链接，冒充即破铁律 1 的「不杜撰」。


### 7.7 积分不足专项处理（`INSUFFICIENT_CREDITS`，必须执行）

检测到积分不足（`INSUFFICIENT_CREDITS`，或任何「积分不足／余额不够」提示）时：**不要只丢错误码**，必须主动给出拿积分最快的路径。固定话术：

> 你的 Cue 积分不足，本次任务未能启动。三个办法：
> 1. **等次日免费额度**（成本最低）：每天送 10 分——额度口径**以服务端返回为准**，本文不报死数。
> 2. **邀请好友得积分（推荐）**：打开 <https://cuecue.cn/>，点击页面**左下角**「获取专属邀请链接」，分享给好友——好友加入后你再得积分。
> 3. **直接充值**：前往 <https://cuecue.cn/pay> 订阅。

规则：

- 提示要**主动、简短、可点**——把「首页」和「左下角」这两个关键动作说清楚，不让用户自己找入口。
- 积分不足**不要重试**（`retryable: false`），也**不要换 query 绕**——换 query 只是换个扣费动作，不解决余额问题。
- 用户回复已充值／已邀请后，用**完全相同的命令**重跑（同 §7.6 的续接口径）。
- **无人值守场景（提醒触发）专属纪律**：提醒是定时跑的，届时无人可问。积分不足时**禁止**反复重试或换 query，只做陈述并明确回报「Cue 积分不足，本次未跑研究」，同时把上面三条路径附在回报里，等用户回来处理。**不许把「没跑成」粉饰成「跑完了但没结论」**。
- 计费事实一律只转述服务端返回，**不报死数**（同铁律 5）。
